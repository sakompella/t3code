# This fork

`sakompella/t3code` is a personal fork of [pingdotgg/t3code](https://github.com/pingdotgg/t3code). Its main addition is support for [Prime Agent](https://github.com/PrimeIntellect-ai/prime-agent). Upstream PRs are not a goal. These rules override the upstream guidance in `AGENTS.md` where they conflict.

## Priorities, in order

1. **It works for the owner, and they stay productive.** This comes first, even when a change moves the fork far from upstream.
2. **Maintainability.** Keep code simple. Delete workarounds that a better fix replaces. Don't keep fork code because it already exists.
3. **Closeness to upstream `main`.** A minor concern. Prefer upstream's features and patterns when they do the job, and avoid needless divergence, but never at the cost of 1 or 2.

## Topic branches

The fork is kept as topic branches on upstream `main`. `FORK-TOPICS` lists them in merge order as `<topic> <parent>`, where the parent is `upstream` or an earlier topic, and topic X lives on branch `topic/X`. Today there are seven, in merge order:

- `meta` on upstream: this file, `FORK-TOPICS` and `scripts/fork-topics.py`.
- `tailwind-src-scan` on upstream: Tailwind scans only `apps/web/src`.
- `image-scaling` on upstream: images over 2000 px are scaled before Claude and Pi/Prime Agent inline them.
- `electron-run-as-node` on upstream: `ELECTRON_RUN_AS_NODE` goes only to the children that run Electron as Node.
- `failed-turn-sweep` on upstream: a failed turn does not start a worktree cleanup sweep.
- `provider-switch-guidance` on upstream: agent instructions delegate to another provider only for a missing capability.
- `fork` on `meta`: everything else, mostly the Prime Agent provider.

The feature list below covers every topic and stays in this file. More topics get carved out of `fork` once each builds on its own from whole hunks. When two features share a hunk, an ordinary refactor commit on `fork` first moves their lines apart. A topic whose code `fork` imports goes on `meta`, and `fork` is restacked on it. What blocks the next carves (checked 2026-10-21):

- Prime Agent provider: upstream plus every `packages/` change of `fork` leaves 9 `apps/server` errors. They come from exhaustive switches over new variants (the `rollback_summary` item, the `html_render.record` command, the `app_thread.reparented` event) and the required `now` of `ProjectThreadAwarenessV2Input`. So the server halves of rollback summaries, `html_render` records and nested subagents would have to come with it.
- Rollback: its contracts and most of its server half now carve cleanly. `ChatView.tsx` shares an import hunk with heartbeats. Hunks in `WireProjection.ts` (subagent text), `V2ItemInspector.tsx` (long notices), mobile `thread-work-log.tsx` (syntax highlighting) and `threadActivity.ts` (run-fold), and the `pendingHeadMove` guard in `Orchestrator.ts` (failed-steer queue) are shared too.
- Syntax highlighting: the web half and `entryCode.ts` carve cleanly. On mobile, `thread-work-log.tsx` shares hunks with rollback summaries and notice labels, and `threadActivity.ts` imports `pythonCellLabel` (the Prime tool display) in the same statement as the highlighting helpers.
- The thread-switch typing fix shares a `Sidebar.tsx` import hunk with snooze and settle.

**Rules.** The daily sync rebuilds the topics on `upstream/main`; nothing rebases `feat/prime-agent-on-main`. Every worker branch starts from the topic it changes and lands into that topic with `--no-ff` (`scripts/fork-topics.py land <branch> <topic>`), never into `feat/prime-agent-on-main`, never fast-forwarded or squashed.

- `feat/prime-agent-on-main` is the integration branch: upstream `main` plus one `--no-ff` merge per topic. `scripts/fork-topics.py rebuild` rebases each topic onto its parent's new tip and builds `integration/candidate`. After the checks pass, `promote` tags it `integration/YYYYMMDD-N` (UTC date), and feat is reset to that tag. Nobody commits on feat. Deploy only from an `integration/*` tag.
- A worker branch starts with `git worktree add -b <branch> <path> topic/<X>`. A change that needs several stacked topics starts from the highest one. `land` rebases the branch onto the topic if the topic was rebuilt meanwhile, so the branch must not be checked out anywhere else then.
- A fix for an upstream change is an ordinary commit on the topic that owns the code. Never edit a landing merge: a rebuild replays merges from their parents and would drop the edit.
- A topic with more than 20 commits above its parent is collapsed into one commit (`collapse <topic>`). The originals stay under `archive/topic/`, landed worker tips under `archive/worker/`, and the history before the migration under the tag `archive/fork-history-20261019`. `Squashed-from:` trailers name the original commits. To find who wrote an older fork line, blame the archive tag.
- A new topic is a `<name> <parent>` line in `FORK-TOPICS` on `topic/meta` plus `topic/<name>` created on its parent. A carve also moves its code out of `topic/fork` and must pass `rebuild --same-tree-as <last tag>`.
- Only `archive/*` tags and deployed `integration/*` tags are pushed to `origin`.

## Prime Agent

- **Don't change Prime Agent.** No fork, no local Nix patches. The owner uses it for most of their work outside T3. Fix integration problems in T3.
- **A T3-shipped Prime Agent extension is a last resort.** Use one only when it gives a material gain that T3-only code can't. Keep it minimal. T3 already loads one (`packages/provider-pi/src/server/mcpInjection.ts`).
- **Target the version the owner runs now**, installed through `numtide/llm-agents.nix`. As of 2026-10-04 that is 0.9.8 (TypeScript). The owner's 0.10 fork (`sakompella/prime-agent`, Rust) is supported beside it as a second flavor, and 0.9.8 behavior must not change for it. Don't add compatibility code for versions nobody here runs. Do rely on what Prime Agent's RPC actually offers rather than on a version number, so another machine on another version fails clearly instead of silently. Prime Agent 0.9.9 is a Rust rewrite whose RPC has no daemon attach, observation or subagent list. Expect integration work when it ships.
- **Prime Agent sessions see exactly one tool, `ipython`.** T3 features reach the agent through the kernel and the `t3-code` MCP server, never as native tools.

## Providers

Keep upstream's providers even if unused. Removing them saves little and adds a large diff.

## What this fork changes

Changes against upstream `main`, grouped by feature. Each item says what changed, then why when that isn't obvious. Upstream PRs are not planned, so the reasons live here rather than in PR descriptions. When you change fork behavior, update this list.

### Prime Agent provider

- **Prime Agent is a provider.** It runs through upstream's Pi RPC adapter as a second "flavor" (`packages/provider-pi/src/server/flavor.ts`), with its own settings, client definition, picker entry and user guide (`docs/user/providers-prime-agent.md`). Most Prime-Agent-only logic lives in `packages/provider-pi/src/server/primeAgent*.ts`. Two pieces live outside it. Session-scoped child threads (`childThreadScope`) are stored by `ProviderSessionManager.ts`, and the kernel-caller branch of `html_render` is in `mcp/toolkits/html/handlers.ts`.
  - Why not a new adapter: Prime Agent is a fork of Pi and speaks the same RPC protocol; reusing the adapter keeps the diff in one place.
- **Prime Agent sessions see one model tool, `ipython`.** T3 features reach the agent through the kernel and the `t3-code` MCP server, using a bundled `t3-code` skill. If `t3-code` isn't declared in Prime Agent's global settings at this server's endpoint, the session still opens kernel-only and shows the exact entry to add. The T3 extension still loads, for the permission hook, in-place rollback and the OpenRouter output cap.
  - Why: the owner's rule is one tool. Prime Agent 0.9.8 reads MCP servers only from the global settings file, so T3 can't supply the server at launch. Without the permission hook, Supervised mode would run every tool unchecked.
- **The Prime Agent 0.10 fork is its own flavor** (`PRIME_AGENT_FORK_FLAVOR`, shown as "Prime Agent (fork, 0.10)"). When a session opens, the adapter reads `prime-agent --version` (`flavor.ts` decides). A version below 0.10 is 0.9.8's flavor if its `--help` offers `--mode rpc`; T3 never sends 0.9.8 `--capabilities`, because 0.9.8 takes an unknown flag as an extension flag and runs print mode. From 0.10 on (prereleases included), T3 runs exactly `prime-agent --capabilities` and launches the fork only if it exits 0 with one JSON object whose `fork` is `t3fork`, whose `contract` is 1, which has a string `version`, and whose `rpc` list names every command the adapter sends (`FORK_COMMANDS_T3_CALLS`; more are fine). Anything else is not launched, and a version suffix counts for nothing: stock 0.10 ("Unknown option", exit 1) fails with "stock Prime Agent 0.10 is not supported; install the T3 fork", and a malformed answer, another marker, another contract or a missing command fails with its own reason. This applies to sessions, the status check and text generation. T3 remembers a launchable answer for the binary file (the path it launches, its real path, size, modification and change time, and inode) and asks again when the file changes, so the extra probe runs once per binary. A shim or wrapper script that picks its target at run time is identified once per server process. A refusal is never remembered. The fork rejects `--extension`, `--no-extensions` and `--no-tools`, so T3 passes none of them. It also leaves the user's extension and tool launch arguments out of every fork launch (sessions, `--fork` helpers, discovery), and says so in Settings and in the thread's first turn. The kernel-MCP route gets its credential and skill without the extension. Rollback uses the RPC's `navigate_tree`, and T3 sends the rollback notice with the next prompt. Only this flavor can leave a summary of the discarded turns (`providerCanSummarizeRollback`; `navigate_tree` with `summarize` and the user's `customInstructions`). `navigate_tree` has no timeout, since abandoning it would not stop the move or its summary model call, and a rollback whose entry is already off the active branch (a retry) does not navigate again, so it never summarizes twice. A summarized rollback that cannot read the active branch fails instead of navigating. The orchestrator checks a rollback against the capabilities of the session hosting the provider thread, because the driver's own capabilities describe 0.9.8. The provider thread's head ref names the entry the rollback moved before, until the fork accepts a prompt carrying the notice (its success ack, not the send) or, on reopen, returns a readable `get_fork_messages` listing without that entry. A failed listing, or one with a message that has no entry id, confirms nothing: the mark stays. T3 never repeats the move on reopen, because a wake may have added conversation on the new branch. While the mark is unconfirmed after a reopen, the thread's first turn shows a "Rollback not confirmed" warning. A heartbeat or message wake that runs before the next prompt does not see the notice. Child threads, heartbeats and wakes use the same frames as 0.9.8. A clipped edit diff (`details.diffs[].truncated`) shows as "edit (diff truncated)".
  - Approvals: the fork has no hook to ask before a tool runs, so it offers only Full access, and a session in any other mode is refused. The server runs a stored mode a provider does not offer in its most restrictive offered mode (Full access here). Web and mobile show that mode, and offer only the modes the provider runs, in the composer and the thread settings. The default permissions setting offers and shows, for each selected environment (or project, with its own provider switches applied), the modes of the provider its new threads start on: the default model's provider, or, when that is unset or unusable, the fallback web's `resolveDefaultProviderModelSelection` picks (first ready, then first non-error). Web and mobile share that rule as `providerForNewThread` in contracts, and new tasks and scheduled tasks on web and mobile start on the provider it picks. Mobile's own last manual model pick, kept on the device, still wins for a new task, and Settings does not show it. Across environments it offers only the modes all of them run, and shows "Mixed" when their new threads would run in different modes. Wherever MCP compares a caller's modes with work it would reach (a child, a launch, a message, an interrupt, a cancel, a scheduled task, and the orchestrator's re-check under the thread lock), it uses the mode that work runs in, so a supervised caller cannot reach a fork thread stored as Supervised. The re-check uses the provider and modes a command leaves the thread in, so a provider switch or model change onto the fork is checked too. The calling thread may act on itself in the modes it already runs in, but not broaden them, and a thread it forks is checked as new work. A caller may update or delete a scheduled task by the rule that let it create one: a task bound to its own thread runs as that thread.
  - Limits: text generation (titles, commit messages, pull request content, branch names) is refused because the fork cannot turn its tools off, and `$skill` chips and the OpenRouter output cap from the extension are gone. The fork's daemon workers do not yet see T3's per-session environment, so the kernel-MCP credential may not reach them. T3's tools will move to the fork's native `t3` module (Prime fork slice 3).
- **Prime Agent opens a thread by launching on its session** (`--resume <session file>`), not by switching sessions after launch.
  - Why: in 0.9.8, replacing a session at runtime (`switch_session`, `new_session`) drops its agent-messaging, `agent_observe` and heartbeat support, so a T3-hosted parent couldn't message its subagents. Plain Pi still switches sessions.
- **Stop and reopen keep the same session.** Prime Agent gets up to 15 s to close cleanly before a forced kill, and a launch or resume refused with "Session is already active" retries the same session for up to 15 s.
  - Why: the old 1 s kill cut off Prime Agent's clean close, so its daemon held the session for 30 s. The next message then failed to resume and started a fresh session with a context handoff, which lost the subagents.
- **Lost events are rebuilt from Prime Agent's stored conversation** (`primeAgentReconciler.ts`). At settle, on reconnect and on a backed-off timer while background work exists, T3 reads `get_messages` between two `get_state` reads, which must show the same history: the same tree leaf on the 0.10 fork, whose `messageCount` spans every branch and leaves out stored notices, and the read's message count on 0.9.8. It adds replies, tool results and follow-up turns it never received. It also settles subagent cards from the notices the parent stored. Nothing is added twice. Unknown outcomes stay unknown.
  - A running turn does not wait for settle when its stream moves past a reply or tool whose end never came (a tool starts, the next reply starts, or the turn ends). T3 reads `get_messages` once then and completes the stored reply or tool result in the place it first appeared. If that read does not find it, a cut reply stays open until the settle read and is never shown as final.
  - Why: under load, the Prime Agent daemon drops events for slow clients and sends a catch-up snapshot, which RPC mode discards. On 2026-10-04 seven replies and many "finished" updates never reached T3. One reconciler replaced several piecemeal repairs. On 2026-10-08 a reply lost its end mid-sentence and showed cut off for 5 minutes, until its turn settled.
  - Limit: a reply recovered after its turn ended appears in the run active at that time.
  - Limit: Stop ends a cut reply with an aborted copy that stock stores under a new timestamp. T3 holds the copy until a history read places it. When the stream and the history cannot prove which reply the copy ended, T3 keeps them apart, and the reply shows its cut text. One such miss: a live copy that holds exactly what the reply showed, next to an older unseen copy that also fits. RPC mode drops the daemon's `meta.sequence`, so T3 cannot see the gap between them. Forwarding the sequence would close it.
  - Limit: A failed attempt removed by an unseen retry can be shown as that retry when its aborted copy still holds the text T3 showed. The retry keeps the attempt's row; later runs stay separate. A stored completed/failed retry reply or compaction summary vetoes that match, leaving distinct rows.
- **An oversized RPC record fails loudly.** A record over upstream's limit (two MCP image budgets plus 8 MiB, about 232 million characters) fails every pending request with `PiRpcRecordTooLargeError`, and reading resumes at the next line.
  - Why: upstream used to drop such lines silently, so a long session's `get_messages` vanished and the request hung. Upstream has since raised the limit far above the largest real history (about 13 million characters); the fork keeps the loud failure.
- **A slow `get_state` reply no longer kills a busy session.** Probes allow more time on a busy machine, and a probe that found no commands keeps the known ones.
  - Why: missed status replies under heavy load were read as a dead process, which killed working sessions.
- **Subagents.** They show as background work, with their own read-only child threads. A child's terminal update reaches the parent even after the run that started it has ended. A nested child gets its own thread, whose parent is its parent child's thread, and its card is drawn in that parent child's thread. If T3 has not seen the parent child yet, both go under the root, and both move on the nested child's next update after the parent child appears. A parent child that finished before T3 saw it never appears, so its nested children stay under the root. The nested child's record stays on the root thread, so the root's subagent tray nests it under its parent child. The record goes on the same root run as its parent child's record while the parent child is still on its task and that run did not fail or get interrupted, else on the live root run. A finished card shows the child's last reply in full when T3 saw it, else Prime Agent's short preview. A finished child stays known, so its follow-up replies still reach its thread, which shows it working again until the follow-up ends. Shell jobs and kernel jobs are tracked as background work too.
  - Child threads are stored by the session, once, not by the runs listening to it. A child can start and work while no run of the parent thread is live (a nested child after its run's turn ended, or a finished child's follow-up), so no single run can own its thread. A child thread write that keeps failing is logged and dropped rather than ending the session.
  - Limit: a nested child stored before nested lineage existed keeps its card on the root's timeline, and its thread still names the root as its parent, so Lineage lists it under the root from every thread. Only the root's projection holds the records that could correct it, and a child's Lineage panel does not load that projection.
  - Limit: T3 cannot answer a subagent's dialog. Stock Prime Agent 0.9.8's RPC observation drops a child's dialog requests, and its daemon refuses another client's attach to a child of a T3-owned session ("Unknown active session"), so no T3-side recipient can exist. T3's own approval prompt therefore blocks a subagent's tool at once, with a reason telling it to run the thread with full access. Another extension's child dialog with no timeout waits until the child is stopped.
- **Self-wakes.** Heartbeats, subagent messages and background-job completions continue the thread as a new run with a notice saying why, instead of ending it. The run uses upstream's buffered continuation for Pi extension wakes; Prime Agent offers it only once the agent replies, so the notice can name the cause. A message the user sends while a wake still runs joins it as a steer.
  - **A wake keeps the user's settle.** Only a message the user sends (including their scheduled tasks) un-settles a thread. A settled thread still leaves the settled shelf on web and mobile while a wake needs the user: a pending approval or question (its own or a subagent's), or a run that failed after the settle. Its completion does not move it, but still sends the completion alert. A server restart note (`restartContinuationOfRunId`) is a wake too. Wakes run on a settled thread, so the fork relies on upstream's worktree cleanup rule (#19748): "settled for N days" counts from the later of the settle and the worktree group's last activity.
    - Why: every wake used to clear settle, so a background command finishing or a heartbeat put a parked thread back on top of the inbox.
  - **Snooze is strict.** Only its timer or an explicit Unsnooze ends a snooze (Wake in the menus, Wake now in the open thread, dragging the row out of the shelf, Undo, or `unsnooze` in the `t3-code` thread tool). Nothing the thread does or receives ends it early: finished commands, subagent and delegated results, heartbeats, approvals, questions, failures, finished runs, and new messages, including the user's. The agent keeps working, including a usage-limit auto-resume that comes due, and every event and message is still stored; opening the thread shows its status and requests as usual. A snoozed thread also sends no alert: no toast, sound or desktop notification on web and desktop, and no mobile push or Live Activity (the server publishes nothing for it). Auto-settle skips it until the timer ends. Usage-limit recovery arms a snooze only on a thread that is not already snoozed, and only an explicit stop for the same recovery ends one. Pinning does not end a snooze, however it is done, including dragging a snoozed row into Pinned; the pin shows once the snooze ends. Dragging the row into Active is the wake.
    - Why: a snooze that any activity could undo put the thread back on top of the inbox within minutes, because Prime Agent threads keep waking themselves. The old exceptions (approval, failure, finished run) had the same effect.
    - Limit: a request that arrives under a snooze waits, unseen in the inbox, until the timer ends or the user opens the thread. A thread cannot be snoozed while a request is already pending. When the timer ends, nothing announces what happened under it, and a completion or failure that finished meanwhile is never pushed later. The relay dates it by the snooze deadline, which stays on the thread after the timer ends, and by `snoozeEndedAt`, which an unsnooze sets to the earlier of the deadline and now before it clears the deadline (an unsnooze with no snooze to end leaves it alone). Both come from the same thread read, so neither needs publishing to be on at the time or any event ordering. Unsnoozing does not push either; a running thread's Live Activity returns at its next event.
  - **Limit: running `bash()` jobs.** A thread that leaves a `bash()` job running still reads as done when the model stops, as upstream decided for Claude background shells. Prime Agent 0.9.8 gives no sign of whether a job will end or is a dev server that runs for hours, so T3 can't hold the thread as Waiting.
- **Rollback and fork.** Rollback rewinds the session in place instead of forking a session file, and tells the agent its live tool state was not reset. A fork can start from a turn while a later turn still runs. A fork or rollback cuts at the first later turn that has a captured user entry. Turns with only a synthetic ref (wakes, continuations, `/compact`, and some failed turns) bound nothing and are skipped, with a logged warning. If one of them did have a user entry, the cut keeps that entry; it never drops one before the target. A fork the adapter refuses on protocol grounds is not retried by the effect worker.
- **Turn lifecycle repairs.** Tools whose end event never arrived are closed when the turn ends. A turn whose closing events were dropped still settles. A pending retry is cancelled before T3 replaces the session.
- **Display of tool calls.** Python cells show their code, bash cells show as commands, and edits show relative paths.
- **Pages from `html_render` show inline.** Prime Agent calls T3's tools from Python, so its tool row is a `python` cell that only prints the result, and clients never showed the page. When a driver that calls T3 from its kernel (`callsT3ToolsFromKernel`) publishes a page, the handler records it in the caller's run as its own `html_render` tool item (`html_render.record`), the shape Claude's native row has. Clients and thread deletion read it with no change. Once the record starts it can't be cancelled. A record that never committed removes the page and fails the call; one that committed keeps it even if its reply was lost. When T3 can't tell which happened, it keeps the page and fails the call saying so; a stray file beats a timeline item pointing at a missing page. A thread deleted during publication refuses the record, and a caller whose provider is no longer registered fails before publishing. Other providers' own `html_render` rows already carry the page, so they get no second item.
  - Why not read the printed output: it is Python's repr of the result, not a format T3 controls.
  - Limit: pages published before this change stay as printed output.
- **Compatibility policy.** The model manifest marks Prime Agent 0.9.6 and later as supported and recommends 0.9.8 or later.
- **Diagnostics.** Each subagent update is logged with the run that took or dropped it, and a failed launch reports the end of stderr.

### Usage accounting

- **Usage Cost/Tokens includes Prime Agent session logs**, including its subagent sessions (`session-artifacts`), disabled accounts and custom agent homes (`PRIME_AGENT_CODING_AGENT_DIR`). Upstream reads Pi's logs; Prime Agent writes the same format, so its reader (`provider-pi/src/server/usage.ts`) reuses Pi's parser under its own series. Copied responses count once per server. A parent response a fork or rewrite saved with its subagents' usage folded in counts at its own usage, read from the `child_usage_attributed` entries; a late attribution reparses only its changed file to correct cached totals. Summaries go under upstream's `Tools/summaries`. Saved model costs win; zero or missing costs fall back to model pricing. Web and mobile show separate Pi and Prime Agent series.
  - Why: the hub quota connection supplies limits, not durable request history. Local logs cover agent work without an always-on hub collector. Other hub clients are not included, and copied history on separate machines may still count twice.

### Prime Agent UI (keep)

- **Heartbeat line.** Threads publish the heartbeats their session runs, and web and mobile show them in a quiet line above the composer.
- **A heartbeat run is a routine check, not a finished task.** The wake notice records which heartbeat fired (`heartbeat` notification source), and the thread shell carries the latest run's trigger (`latestRunTrigger`). A heartbeat run that completes is routine (`isOrchestrationV2RoutineRun`). For a routine run:
  - Web and desktop show no "Thread completed" toast, sound or notification. The relay publishes nothing, so mobile gets no push and no Live Activity.
  - It does not mark the thread unread on web or mobile, and Mark unread rewinds to the last run someone asked for. The shell's `latestTaskRunCompletedAt` carries when that run ended, so an unseen completion from before the check stays unread.
  - It is not thread activity for auto-settle, so a thread with a heartbeat still goes stale and still settles when its pull request merges.
  - A heartbeat's prompt never counts as the latest user message, so "Last user message" ordering (project order, the command palette's recent threads, mobile home) ignores it.

  Failures, approvals and questions from a heartbeat run alert, mark unread and count as activity as usual. A routine run neither alerts nor repeats an earlier completion alert. Shell updates are coalesced, so the web coordinator reads a routine run as standing for the latest run someone asked for (`latestTaskRunCompletedAt` and `latestTaskRunStatus`). A user's completion that a check started or ended in the same update still alerts once, when the check ends. A task that failed, was interrupted, or comes from a server that sends no status never alerts as completed.
  - Why: Prime Agent threads with a heartbeat finished a run every few minutes, and each one alerted as if the task were done. Prime Agent gives no typed "nothing new" signal, and reading the reply text would be a guess, so the trigger decides: a check's end is execution finishing, and the user learns of real news through failures and requests or by opening the thread.
  - On the wire, the source is sent as `background_task` with `work: "heartbeat"`, so clients from before it still decode it. Servers from before it send no trigger, which clients read as a run someone asked for.
  - Not done: alerting when a check deletes its own heartbeat (the watch ended). Prime Agent reports heartbeats only as a list read at settle, and T3 clears that list when the session stops or the server restarts. Read later, every earlier check would then look like it ended its watch. Doing it right needs the outcome decided once at settle and stored on the run, and an agent may also delete and recreate a heartbeat to change it.
  - Limits: every successful check is quiet, including one that reports good news or a problem in its reply text. Nothing stored tells a no-change check from a meaningful one, and T3 does not guess from the reply text.
  - Whether a wake un-settles or un-snoozes a thread is the settle and snooze policy's decision, not this one.

- **Background-work banner.** Live subagents show as a tree in the composer banner, including while a turn is running.
- **Notices.** Prime Agent marks routine notices as info or progress, and they render as quiet rows. Finished progress notices disappear. Refinement outcomes show as notices.
  - **"Finishing up…"** is shown while Prime Agent reviews its harness after the final reply. Without it the turn looks stuck, because Prime Agent emits nothing during that review. The row appears only after 1.5 s.
- **Cache-miss notices.** A Prime Agent thread shows a warning notice when a parent reply re-billed most of the prompt the previous reply cached, for example "Cache miss after 10m idle: 45k tokens re-billed (~$0.14)". Misses below 20k tokens and $0.10 stay quiet. The text says only what usage shows: a model switch, or an idle gap past 5 minutes. Plain Pi shows none. The detector is T3's own (`primeAgentCacheMiss.ts`); Prime Agent, the protocol and settings are unchanged, and there is no running total.
  - Why: a cold cache bills the whole prompt again, and nothing in a T3 thread said so.
  - How: the baseline is the previous reply's prompt. It is seeded from `get_messages` when T3 attaches, so the first reply after a reopen is compared with the last stored one, and older misses in that history stay silent. A live reply carries the parent's own usage. A stored reply may have its subagents' usage folded in, so a stored folded reply resets the baseline instead of counting. A reply counts once, by its response id or else its timestamp, so a catch-up read never repeats a live notice; an equal timestamp alone never hides a distinct reply. The notice reads live and stored replies by this identity, before the reconciler's coarser timestamp key can call them already seen. Compaction, branch summaries and rollback reset the baseline; a summary counts once by role and timestamp, so one sharing a timestamp with a counted reply still resets, and a re-read of it never wipes a newer baseline. Prices come from the reply's own costs, and an unknown cache-read price counts as free.
  - Limits: a folded stored reply leaves no baseline, so the reply after it is not compared. A reply that arrives after a newer one was counted is history and does not move the baseline. Replies without a response id and with the same timestamp count as one.
- **Long notices expand.** A long notice can be opened to read all of it, and a notification with no detail no longer opens an empty panel.
- **Syntax highlighting** for shell commands and Python cells in tool rows, on web and mobile. Mobile shows the exit code under the highlighted source.
- **Prime Agent's icon is its initials, and the instance badge skips it.** Prime Agent has no official mark, so web and mobile draw the instance initials as its glyph. An accent-color or shared-driver badge would repeat them on top, so the badge is not drawn for a glyph that already is the initials. Both tint the initials with the instance's accent color instead.

### General fixes

These aren't Prime Agent-specific.

- **Replies to steers and notifications stay visible** inside a folded run on web and mobile, and each segment between them folds separately. Before, only the run's last reply showed.
  - Why: a single fold for the whole run hid later work above earlier steers, so the collapsed view broke time order. Each segment now has its own "Worked for" row in place, timed and expanded on its own. A run without steers or notifications still has one fold. Segment keys and labels are shared in `packages/client-runtime/src/state/runFold.ts`.
- **A steer sent to a turn that just ended is no longer lost.** If the turn failed, the steer runs as the next run. If it was stopped, the steer goes back to the held queue.
- **`ELECTRON_RUN_AS_NODE` is passed only to children that run Electron as Node.**
  - Why: it leaked into every spawned process. Agents and tools that launch Electron apps then started bare Node instead.
- **Faster quit.** Stopping a Pi session returns as soon as the process exits. When the desktop app force-kills the backend after its grace, the kill does not cut Prime Agent's 15 s close on macOS and Linux, because Prime Agent runs in its own process group and already has SIGTERM.
- **A failed turn does not start a worktree cleanup sweep.** With worktree cleanup on thread deletion turned on, upstream sweeps when a session reports `stopped` or `error`. Pi, Prime Agent and OpenCode report every failed turn as `error` on a session that stays live, and the sweep's own check keeps a worktree whose session is live, so that sweep could never free its worktree. Only `stopped` and thread deletion start one now.
  - Why: each sweep runs git in every worktree (6.9 s median on the owner's data), and a usage-limit or provider error fails turns in bursts.
- **Startup.** Requests that arrive after the port is bound, but before the server is ready, get `503` with `Retry-After` instead of hanging.
- **Preview.** Evaluating a void expression, like `click()`, returns `null` instead of failing.
- **Rollback.** A fork no longer brings back turns that were rolled back first.
- **Undo after a failed run.** Undoing a message whose previous run failed or was cancelled before it captured a checkpoint, or was rolled back, rolls back to the last earlier run with a checkpoint, else to the thread start, and discards the runs in between. Upstream looked only for the previous run's own checkpoint and failed with "Rollback target run ordinal N is unavailable" before reaching the server.
- **Rollback across a provider switch.** A rollback can target a turn of an earlier provider, for example the first Prime Agent message after Codex. Upstream refused it ("belongs to provider thread"). The active provider thread now rewinds to its own last kept turn at or before the target, else to its start. A context handoff it received in a discarded turn goes out again with its next turn, minus the discarded runs; one that held only discarded runs is superseded.
  - Another root provider thread the rollback discarded turns from cannot be rewound without its session, so it drops its native conversation. Switching back to it starts a fresh native conversation with the kept history as a full handoff (for example Codex 1, 2, Prime Agent 3, roll back to 1: Codex no longer holds turn 2). That run also restarts the row's `firstRunOrdinal`, so a later rollback rewinds the fresh conversation by its own turns only, never by a turn of the dropped one, and a fork from an earlier run uses portable context instead of a native fork. Its earlier native history is no longer linked to the thread.
- **Image attachments are scaled for Claude and Pi/Prime Agent.** A long side over 2000 px is scaled down to 2000 when the server inlines the image (`apps/server/src/provider/providerImage.ts`, reached from the Claude adapter and `ProviderHost.readImageForProvider`). The stored file and the path shown to the agent stay the original.
  - Why: once a conversation held more than 20 images, Anthropic rejected every request because one image was over 2000 px, and the history kept resending it. Uses `@napi-rs/image`, loaded on first use; an image it cannot decode is sent as stored. Codex, ACP, Cursor, OpenCode and Muse are not scaled. Images already in a Pi or Claude session keep their size.
- **Pi and Prime Agent thinking levels show a default on every model.** Discovery marks the level Pi has active, clamped into each model's levels, as that model's default, as long as the active model can think. Upstream (#17835) limited it to the active model, but `set_model` carries the session's level to the next model, so the thinking control on any other model showed no level and no menu mark. A draft still sends no thinking option, and Pi applies the same level. The 0.10 fork remembers the level asked for and reports it clamped to the active model, so Extra High reads as High on a model without it; a model then gets a default only when every level the report could stand for clamps to the same one there.
- **Provider switching.** Agent instructions say to delegate to another provider only for a capability the current one lacks (for example Codex computer use), not to reach a model family. Prime Agent can run GPT models itself.
